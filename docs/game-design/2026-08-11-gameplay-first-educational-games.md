## 文書の目的

ManabiNoteに追加する新しい知育ゲームについて、候補の比較、採用方針、最有力候補である「どうぶつレスキュー迷路」のゲーム仕様とMVP範囲を記録する。

この文書は企画・設計段階の基準とし、実装中に判断が分かれた場合は「ゲームとして遊んでいるうちに、結果として知育になる」という方針を優先する。

## 背景

現在のゲームは、文字、数字、漢字、文などの問題に回答する形式が中心になっている。今後は問題形式を増やすだけでなく、ゲームの攻略そのものに次の行動が必要になるゲームを追加する。

- 考える
- 覚える
- 比較する
- 試す
- 予測する

## 基本方針

- ゲーム性を知育要素より優先する。
- 問題集のような画面構成にしない。
- 正解・不正解を繰り返すだけの進行にしない。
- 入力するたびにゲーム世界の状態が変化するようにする。
- 間違った操作には赤い不正解表示を出さず、世界の反応で結果を伝える。
- 試行錯誤を強く罰せず、やり直しや1手戻しを用意する。
- 幼児が文字を読めなくても、絵、動き、色、記号でルールを理解できるようにする。
- タップとスワイプを中心にし、小さな操作対象や精密なドラッグを避ける。
- 1プレイまたは1ステージを数分以内にする。
- ステージ、スコア、収集、コンボなどを追加できる構造にする。

### ゲーム性を確認する基準

次の条件を満たすことを、企画およびレビュー時の基準とする。

1. 学習用の文字説明や正解演出を取り除いても、遊びとして成立する。
2. プレイヤーの操作が盤面やキャラクターの状態を直接変える。
3. 成功には観察、記憶、比較、順序、先読みのいずれかが必要になる。
4. 失敗したときに、別の方法を試したくなる。
5. 同じステージでも、宝物や目標手数など別の目的で再挑戦できる。

### 候補ごとの判断

#### どうぶつレスキュー迷路

ゲーム性、理解しやすさ、知育との自然な融合、拡張性のバランスが最もよい。移動、救出、鍵、扉、敵などが同じ盤面上で作用するため、問題画面を使わずに方向感覚、順序、ルート探索、先読みを使わせられる。

#### おみせやさん

注文カードに回答するだけでは既存ゲームの言い換えになる。商品の流れ、カゴの容量、複数の客、待ち時間などの状況管理を中心にすればゲームとして成立する。

#### モンスター合体

短い操作で結果が出て再プレイ性が高い。ステージ追加より、新しいモンスター、盤面、特殊能力、進化図鑑の追加が中心になる。出現運に左右されすぎない調整が必要になる。

#### パイプ・道つなぎ

知育要素が攻略へ自然に組み込まれる。単独ゲームにもできるが、レスキュー迷路内の橋や水路を直す仕掛けとして取り込むこともできる。

#### 宝探し

ヒントから場所を絞り込む体験はよい。ただし、候補を論理的に減らせない配置では当てずっぽうになる。方向、距離、地形を組み合わせて推理できる設計が必要になる。

#### 荷物積み込み

図形と回転を自然に扱える。一方、小さな画面でのドラッグ、回転、衝突判定、指で隠れる問題があり、スマートフォン対応の難易度が高い。

#### 料理

食材を正しい順番に選ぶだけでは順番問題になる。流れてくる食材、限られた調理台、同時に来る複数注文を扱うことで、判断と段取りをゲームにする必要がある。

#### 影絵モンスター

図鑑やレア要素を付けても、中心が選択問題ならクイズ構造のままになる。将来的には探索中にシルエットや痕跡を発見する仕組みへ発展させたい。

#### ロボット誘導

順序と先読みを自然に使えるが、最初から命令列を並べると教材に見えやすい。レスキュー迷路の後半で、仲間ロボットを操作するギミックとして導入する方法もある。

#### 簡易タワーディフェンス

ゲーム性と拡張性は高いが、敵、味方、相性、進行速度、難易度調整、アニメーションの実装規模が大きい。最初のゲーム性重視タイトルとしては後回しにする。

## 採用方針

最初に実装する候補は「どうぶつレスキュー迷路」とする。

優先する理由は次のとおり。

- 文字を読まずに基本ルールを理解できる。
- 移動そのものに空間認識と方向感覚が必要になる。
- 鍵、扉、スイッチ、敵によって順序と先読みを自然に追加できる。
- ターン制にすることで、反射神経ではなく考えることを中心にできる。
- 手作りステージをデータとして追加しやすい。
- ReactとCSS GridでMVPを実装でき、Canvasや物理エンジンを必要としない。
- 他候補の一部を将来のギミックとして取り込める。

メニュー項目を増やしすぎないため、新しい「あそび」または「ぼうけん」カテゴリを追加し、その中で1本のゲームとして成長させる方針を候補とする。カテゴリ名は実装開始前に決定する。

## どうぶつレスキュー迷路

### ゲームの中心となる体験

プレイヤーはキャラクターを1マスずつ動かし、迷路内の動物を助けて出口を目指す。プレイヤーが1回行動すると敵や仕掛けも1回反応するターン制を基本とする。

ゲーム内では問題文を表示しない。鍵がない扉は鍵の記号を表示する、動物を残したまま出口へ行くと残っている動物の絵を表示するなど、世界の反応によって必要な行動を伝える。

### 基本ゲームループ

1. ステージマップからステージを選ぶ。
2. 盤面を見て、動物、出口、鍵、障害物の位置を確認する。
3. 隣接マスをタップするか、上下左右にスワイプして1マス移動する。
4. 動物を救出し、必要に応じて鍵やスイッチで道を開く。
5. 必須の動物をすべて助けて出口へ到達する。
6. 肉球スタンプ、宝箱、救出した動物を受け取る。
7. 次のステージを解放し、「つぎへ」または「もういちど」を選ぶ。

### 画面構成

#### ステージ選択画面

- 道に沿ってステージが並ぶエリアマップ
- ステージごとの肉球スタンプ
- 救出済みの動物と取得済みの宝箱
- 雲や門で表現した未解放ステージ

#### ゲーム画面

- 上部にステージ番号、救出数、所持中の鍵を表示する。
- 中央に正方形の迷路を大きく表示する。
- 下部に「1手戻す」「やり直す」「一時停止」のアイコンを置く。
- 初回だけ、動く手のアニメーションで操作を示す。

#### クリア表示

別の結果ページへ移動せず、ゲーム盤の上にクリア表示を重ねる。

- 助けた動物
- 獲得した肉球スタンプ
- 取得した宝箱
- 「つぎへ」ボタン
- 「もういちど」ボタン

### 操作方法

- 進みたい隣接マスをタップする。
- または迷路上を上下左右にスワイプする。
- パソコンでは矢印キーでも移動できるようにする。
- 押せる箱は、箱に向かって移動すると1マス押す。

キャラクターを自由にドラッグして任意の場所へ移動させる方式は採用しない。経路と1手ごとの結果を考える要素が弱くなるためである。

### 成功条件

- ステージ内の必須動物をすべて救出する。
- 救出後に出口へ到達する。

### 失敗とやり直し

序盤は基本的にゲームオーバーを作らない。

- 壁へ進もうとした場合は、キャラクターが軽く揺れてその場に留まる。
- 鍵がない扉へ進んだ場合は、必要な鍵の記号を表示する。
- 動物を残して出口へ行った場合は、残っている動物の絵を表示する。
- 敵に接触した場合は、直前の安全地点へ戻す。
- 箱を動かして進めなくなった場合は「1手戻す」で復元できる。

制限手数は失敗条件にせず、追加の肉球スタンプを獲得する条件として使う。時間制限は通常ステージでは使用せず、将来の任意チャレンジに限定する。

## ステージ1～10の案

| ステージ | 新しい要素 | 内容 |
|---|---|---|
| 1 | 移動と救出 | 4×4程度の一本道で、動物を1匹助けて出口へ向かう。 |
| 2 | 壁と分かれ道 | 短い行き止まりを含む迷路で、進める方向を観察する。 |
| 3 | 宝箱 | 出口とは別方向に任意の宝箱を置き、寄り道するか選ばせる。 |
| 4 | 鍵と扉 | 鍵を拾い、対応する扉を開けて動物を助ける。 |
| 5 | 複数救出 | 離れた場所にいる動物を2匹助け、効率のよい順路を考える。 |
| 6 | 動く敵 | プレイヤーの行動後に敵が1マス動く。敵の次の移動先は矢印で予告する。 |
| 7 | スイッチと橋 | 床スイッチを踏むと水上に橋が現れる。 |
| 8 | 記号付きの鍵 | 星の鍵と星の扉、月の鍵と月の扉を使い、複数段階の経路を考える。 |

## 難易度の上げ方

- 盤面を4×4から5×5、6×6へ広げる。
- 分かれ道と行き止まりを増やす。
- 救出対象を増やす。
- 「鍵、扉、スイッチ、橋」の依存関係を長くする。
- 敵の数や移動パターンを増やす。
- 宝箱と最短ルートを両立しにくくする。
- 後半では一部を暗くし、一度見た地形を覚えて進む要素を追加する。

新しいギミックは1～2ステージにつき1つとし、初登場時は失敗しにくい安全な配置で体験させる。難易度は文章や数値を難しくするのではなく、盤面上の関係性を増やすことで上げる。

## リプレイ性

各ステージで最大3個の肉球スタンプを獲得できるようにする。

1. ステージをクリアする。
2. 宝箱を取得する。
3. 目標手数以内、または敵に捕まらずにクリアする。

将来追加できる要素は次のとおり。

- 救出した動物の図鑑
- 動物から受け取る帽子や飾り
- エリアごとの秘密アイテム
- 宝箱の位置が変わるチャレンジ
- 同じ盤面で条件が変わるミッション
- 手作りステージ完了後の自動生成迷路
- 週間チャレンジ

最初から自動生成を主軸にせず、遊びやすさを調整した手作りステージを優先する。

## 他候補を取り込む拡張案

- 宝探しを隠し宝箱や探索ステージとして追加する。
- パイプ・道つなぎを橋や水路を直す小部屋として追加する。
- ロボット誘導を仲間ロボット用の仕掛けとして追加する。
- 影絵モンスターを未発見動物の図鑑として追加する。
- 荷物積み込みを岩や箱で道を作る仕掛けとして追加する。

これらを独立したメニュー項目にせず、レスキュー迷路のエリアやギミックとして追加することで、メニューの増加を抑える。

## データ設計

### ステージ定義

```ts
type StageDefinition = {
  id: string
  width: number
  height: number
  tiles: readonly Tile[]
  entities: readonly EntitySpec[]
  goals: readonly GoalSpec[]
  parMoves?: number
}
```

ステージ定義はプレイ中に変更しない。盤面、初期配置、クリア条件、目標手数を保持する。

### プレイ状態

```ts
type RescueState = {
  stageId: string
  playerPosition: Position
  entityStates: Record<string, EntityState>
  inventory: readonly ItemId[]
  rescuedAnimalIds: readonly string[]
  collectedTreasureIds: readonly string[]
  moves: number
  status: 'playing' | 'cleared'
  history: readonly TurnSnapshot[]
}
```

`history` は1手戻すための盤面スナップショットを保持する。保存量が問題になる場合は、MVP後に差分方式を検討する。

### 操作

```ts
type PlayerAction =
  | { type: 'move'; direction: Direction }
  | { type: 'undo' }
  | { type: 'restart' }
```

### ゲームイベント

```ts
type GameEvent =
  | { type: 'animal-rescued'; animalId: string }
  | { type: 'door-opened'; doorId: string }
  | { type: 'bridge-activated'; bridgeId: string }
  | { type: 'player-caught' }
  | { type: 'stage-cleared' }
```

画面はイベントを受け取り、アニメーションと効果音を再生する。ゲームルール側ではDOMや音声を直接操作しない。

### 進行状況

```ts
type RescueProgress = {
  unlockedStageIds: readonly string[]
  bestStampCountByStage: Record<string, number>
  bestMovesByStage: Record<string, number>
  collectedTreasureIds: readonly string[]
}
```

端末内のlocalStorageへ保存する。既存の全体クリア状況とは別に、レスキュー迷路内のステージ進行を保持する。

## ゲームルールModule

ゲームルールはReact画面から分離し、次の小さなInterfaceを持つModuleへ集約する。

```ts
startStage(stage: StageDefinition): RescueState

applyAction(
  stage: StageDefinition,
  state: RescueState,
  action: PlayerAction,
): { state: RescueState; events: readonly GameEvent[] }

calculateResult(
  stage: StageDefinition,
  state: RescueState,
): StageResult
```

鍵、扉、スイッチ、敵、救出判定の実装はこのModule内部に置く。React側は状態を描画し、操作を渡し、返されたイベントに応じて演出する。

ステージ追加を安全にするため、開発時には次を検証する関数またはテストを用意する。

- プレイヤーの開始地点が1つだけ存在する。
- 出口が存在する。
- 必須の動物が存在する。
- 鍵と扉の記号が対応している。
- 盤面の幅、高さ、タイル数が一致する。
- 基本的なクリア経路が存在する。

## Web実装方針

- MVPはReactとCSS Gridで盤面を描画する。
- 移動はCSS Transformでアニメーションする。
- Pointer Eventsでタップとスワイプを扱う。
- ターン制のためCanvasや物理エンジンは導入しない。
- 迷路領域だけスクロール操作を抑制し、ページ全体との誤操作を防ぐ。
- 盤面ロジックは純粋なTypeScriptとしてテストする。
- PWAでオフラインでも遊べる構成を維持する。
- 既存の動物画像を再利用できるか確認し、不足する主人公、壁、床、扉などを追加する。

- ステージ選択画面
- ゲーム盤上のクリア表示
- 次ステージと再挑戦への導線
- 端末内への進行状況保存
- 最小限の移動、救出、扉、クリア演出
- 最小限の効果音

### MVPに含めないもの

- スイッチと橋
- 押せる箱
- 複数種類の敵
- 霧や暗闇
- 自動生成ステージ
- 着せ替え
- 週間チャレンジ
- オンラインランキング
- アカウント間の進行同期

## MVPの受入条件

- 文字を読まなくてもステージ1の操作と目的を理解できる。
- タップ、スワイプ、矢印キーのいずれかで1マス移動できる。
- 動物を助ける前には出口からクリアできない。
- 鍵を取得すると対応する扉を開けられる。
- 敵の次の移動先が視覚的に分かる。
- 敵との接触後に最初からすべてやり直さなくてよい。
- 1手戻す操作で直前の盤面を復元できる。
- ステージごとの最高スタンプ数と最少手数が保存される。
- スマートフォンの縦画面で横スクロールせずに遊べる。
- 10ステージを順番に解放して最後まで遊べる。
- 全体が問題文、選択肢、正解・不正解の構造になっていない。

## 実装前に決める保留事項

- 新カテゴリ名を「あそび」と「ぼうけん」のどちらにするか。
- 主人公を人、動物、ロボットのどれにするか。
- ステージクリア評価を肉球、星、バッジのどれで表現するか。
- 敵との接触後に戻す位置を、直前位置とチェックポイントのどちらにするか。
- 既存の動物画像を盤面用にそのまま利用するか、小型の専用素材を用意するか。
- 全体のクリア状況へ反映する条件を、最初の1ステージクリアとMVP全6ステージクリアのどちらにするか。
- 効果音をMVPへ含める場合の素材とライセンス。

## 実装開始時の順序

1. 保留事項を決定する。
2. ステージ1～6の盤面を紙またはデータで確定する。
3. ステージ定義とゲーム状態の型を作る。
4. `startStage` と `applyAction` をテスト駆動で実装する。
5. 壁、救出、出口、鍵、扉、敵の順にルールを追加する。
6. CSS Gridの盤面とタップ操作を接続する。
7. スワイプ、矢印キー、1手戻すを追加する。
8. ステージ選択、保存、クリア演出を追加する。
9. 360px幅のスマートフォン表示で操作性を確認する。
10. 子どもが説明なしでステージ1を遊べるか確認し、必要なら演出を調整する。

## 次候補

どうぶつレスキュー迷路と料理ゲームのMVP後は、次の順で再検討する。

1. モンスター合体ゲーム
2. パイプ・道つなぎゲーム
3. おみせやさんゲーム

料理ゲームは複数注文、食材レーン、待ち時間を扱う形で実装した。

モンスター合体ゲームは、4×4盤面をスワイプまたは方向ボタンで動かす簡易2048型として実装した。同じモンスターの合体、連続合体コンボ、スコア、新種発見図鑑、ドラゴン誕生によるクリア、盤面が詰まった場合の終了を含む。文字が読めない場合も、絵の変化と方向操作だけで基本ループを理解できる構成とした。

「パイプ・道つなぎゲーム」は「みずの みち」として実装した。パイプをタップで回転し、水源からすべての花まで、漏れのない一本の水路を作る。直線、曲がり角、分岐、複数の花を順に導入する6ステージ、回転回数による星評価、最終ステージの全体クリア記録を含む。

「おみせやさんゲーム」は「どうぶつマーケット」として実装した。絵と数字の注文を見て、8種類の商品から必要な個数をかごに入れ、不要な商品はかごから戻して接客する。待ち時間、連続接客コンボ、コイン、5人接客でのクリアに加え、後半には最初の商品を取ると注文が隠れる記憶客を導入した。料理ゲームの順序操作とは異なり、数量、分類、短期記憶、見直しを中心にしている。

「宝探しゲーム」は「どこかな？たからじま」として実装した。4×4、5×5、6×6の3島を探索し、外れた場所には宝の方向を示す8方向矢印と、マンハッタン距離に応じた寒い・暖かい・熱いヒントが残る。限られた採掘回数で過去の手掛かりを比較し、3島中2個の宝を見つけるとクリアになる。

「荷物積み込みパズル」は「ぴったり！にづみ」として実装した。形の異なる荷物を選択し、90度ずつ回転させて荷台の指定領域へ配置する。はみ出しや重なりは置けず、置いた荷物を戻して試し直せる。直線、L字、正方形、T字、ジグザグを段階的に導入する5ステージと、操作回数による星評価を含む。

「ロボット誘導ゲーム」は「ロボット GO！」として実装した。上下左右の命令を先に並べて発進し、壁に当たった場合やゴールへ届かなかった場合は命令列を組み直す。後半では電池を1～3個すべて回収してからロケットへ向かう必要がある。6ステージ、実行経路の足跡、試行回数と命令数による星評価を含む。

「影絵モンスター収集」は「シルエットハンター」として実装した。照らされた黒い影と同じ姿を森の5体から探し、制限時間内に6体を捕獲する。連続捕獲コンボ、3段階のライト残量、影の逃走、10種類のモンスター図鑑を含み、名前を読んで答えるのではなく形状比較と探索そのものをゲームループにした。

簡易タワーディフェンスは「もりの まもり隊」として実装した。火・水・葉の3すくみを、3本の道へ守り役を配置して迫る敵を迎撃するリアルタイムゲームにした。3ウェーブの出現順予告、守り役の途中交代、配置に使う種、森の体力、撃退スコアを含む。全ウェーブが実際の配置操作でクリア可能なことをモデルテストでも検証する。

次の候補は、リズム記憶ゲーム。その後は、仕分けコンベアゲームを再評価する。
